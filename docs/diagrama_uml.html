Diagrama de Classes — Versão 1 (Sem Padrão GoF)

Três classes independentes, cada uma com seu próprio método gerar(). Os passos de coleta, processamento e exportação estão duplicados nas três classes.

⚠️
Problema: Não há herança nem reutilização de código. Os passos 1 (coletarDados), 2 (processarDados) e 6 (exportar) são idênticos nas três classes. Qualquer mudança no fluxo exige editar 3 arquivos separados.

🏗️ Diagrama de Classes — Versão 1 Sem GoF

classDiagram class RelatorioPDF { -titulo String -dados String +RelatorioPDF(titulo, dados) +gerar() void -coletarDados() void -processarDados() void -formatarCabecalhoPDF() void -formatarCorpoPDF() void -formatarRodapePDF() void -exportar() void } class RelatorioHTML { -titulo String -dados String +RelatorioHTML(titulo, dados) +gerar() void -coletarDados() void -processarDados() void -formatarCabecalhoHTML() void -formatarCorpoHTML() void -formatarRodapeHTML() void -exportar() void } class RelatorioCSV { -titulo String -dados String +RelatorioCSV(titulo, dados) +gerar() void -coletarDados() void -processarDados() void -formatarCabecalhoCSV() void -formatarCorpoCSV() void -formatarRodapeCSV() void -exportar() void }

Problemas Identificados

coletarDados() duplicado nas 3 classes
processarDados() duplicado nas 3 classes
exportar() duplicado nas 3 classes
Sem herança — classes totalmente independentes
ℹ️
Violações: DRY (Don't Repeat Yourself) — código duplicado em 3 lugares. OCP (Open/Closed Principle) — adicionar um novo passo exige abrir e editar 3 arquivos diferentes, com risco de inconsistência.

Diagrama de Classes — Versão 2 (Template Method Clássico)

A classe abstrata RelatorioGerador define o esqueleto do algoritmo. As subclasses implementam apenas os passos variáveis.

ℹ️
Template Method: gerarRelatorio() é final — nenhuma subclasse altera a ordem dos passos. Os métodos abstract são obrigatórios. incluirMarcaDagua() é um hook — opcional.

🏗️ Diagrama de Classes — Versão 2 Template Method

classDiagram class RelatorioGerador { <<abstract>> +titulo String +dados String +gerarRelatorio() void +coletarDados() void +processarDados() void +exportar() void +formatarCabecalho() void +formatarCorpo() void +formatarRodape() void +incluirMarcaDagua() void +getFormato() String } class RelatorioPDF { +formatarCabecalho() void +formatarCorpo() void +formatarRodape() void +incluirMarcaDagua() void +getFormato() String } class RelatorioHTML { +formatarCabecalho() void +formatarCorpo() void +formatarRodape() void +getFormato() String } class RelatorioCSV { +formatarCabecalho() void +formatarCorpo() void +formatarRodape() void +getFormato() String } RelatorioGerador <|-- RelatorioPDF : extends RelatorioGerador <|-- RelatorioHTML : extends RelatorioGerador <|-- RelatorioCSV : extends

Legenda dos Métodos

final — não pode ser sobrescrito (template)
abstract — subclasse deve implementar
hook — implementação padrão, sobrescrita opcional
private — passo fixo interno
💡
Hook em ação: Apenas RelatorioPDF sobrescreve incluirMarcaDagua() para adicionar "CONFIDENCIAL". RelatorioHTML e RelatorioCSV herdam a implementação vazia.

Diagrama de Classes — Versão 3 (Reflexão + Anotações)

As anotações @PassoRelatorio e @RelatorioConfig desacoplam o executor das implementações concretas.

⚡
Diferença-chave: ExecutorRelatorio não conhece RelatorioPDF, RelatorioHTML nem RelatorioCSV em tempo de compilação. Ele descobre e executa os passos via reflexão Java lendo as anotações em runtime.

🔬 Anotações Criadas @Annotations

classDiagram class PassoRelatorio { <<annotation>> +ordem int +descricao String +obrigatorio boolean } class RelatorioConfig { <<annotation>> +nome String +extensao String +versao String +descricao String }

Diagrama de Sequência — Versão 3 (Reflexão em ação)

Mostra o que acontece quando ExecutorRelatorio.executar(relatorioPDF) é chamado — a reflexão descobrindo e invocando os passos.

Ponto-chave: A seta Executor → Reflect → PDF mostra que o Executor nunca chama PDF diretamente. A API de reflexão localiza e invoca o método concreto, eliminando o acoplamento em tempo de compilação.
